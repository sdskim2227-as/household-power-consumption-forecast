# Claude Code로 이 프로젝트를 어떻게 진행했는가 (계획 + 회고)

처음엔 계획 문서로 시작했다가(스캐폴딩+원본 데이터 배치만 끝난 시점), 정규 파이프라인
(01~13) 완료 후 회고를 덧붙였다. 계획 단계에서 세운 것과 실제로 확정된 것을 구분해서
남긴다. 시간순 상세 기록은 [`worklogs/`](../worklogs/)에 있다.

## 회고 요약 (2026-08-22, 파이프라인 완료 시점)

- **결과**: 선형회귀 R²=0.5039로 최종 1위, 두 기준선(평균값 -0.01·persistence 0.14)을
  확실히 이겼다. 랜덤포레스트·XGBoost는 표본(train 1,128행)이 작아 과적합(XGBoost train
  R²=1.0000)해서 오히려 선형회귀보다 못했다 — 가장 단순한 모델이 이긴 사례.
- **가장 큰 계획 변경**: 타깃 단위를 "다음 시간"에서 "다음 날"로 바꿨다(아래 "타깃 단위"
  행, `REPORT.md` 1장·부록 참고). 사용자가 "다음 시간 예측이 의미 있냐"고 두 차례
  질문하면서 방향이 바뀐 경우 — 계획대로 안 갔지만, 그 덕분에 이 프로젝트의 강점(4년치
  계절성)을 실제로 활용하는 쪽으로 개선됐다.
- **lean 진행**: `seoul-subway-demand-forecast`처럼 하이퍼파라미터 튜닝·시간 누수
  검증·이상치 탐지를 생략했다 — 이미 선형회귀가 기준선을 크게 이겨 결론이 분명했다.

## 무엇을 예측하려는가

[`problem-definition.md`](./problem-definition.md)에서 정한 문제:

1. **가정 사용 패턴 EDA** — 시간대·요일·계절·가전 카테고리별 사용량 구조 (탐색, 예측
   모델의 준비 단계)
2. **다음 시점 전력 사용량 예측 (회귀)** — 이 프로젝트의 핵심. `seoul-rainfall-prediction`·
   `seoul-subway-demand-forecast`처럼 예측이 메인이고, `korea-power-consumption-analysis`
   처럼 EDA가 메인이 아니다.

데이터는 `data/raw/household_power_consumption.txt`(세미콜론 구분, 133MB, 분 단위,
2006-12-16~2010-11-26, 2,075,259행). **133MB로 GitHub 100MB 제한을 넘으므로
`data/raw/`를 이 프로젝트의 `.gitignore`에 추가한다** — 앞의 세 프로젝트와 달리 원본을
커밋하지 않고, `data/preprocessed/`의 집계된(시간 단위 등) 결과만 커밋한다.

**가장 중요한 제약**: 다른 프로젝트와 동일하게, 입력은 항상 예측 시점까지의 값만 쓴다.
타깃은 `shift(-1)`(집계 단위 기준 다음 시점)로 다음 행에서 끌어오고, 입력 피처는 앞당기지
않는다.

## 이전 세 프로젝트와의 차이

| | seoul-rainfall-prediction | seoul-subway-demand-forecast | korea-power-consumption-analysis | household-power-consumption-forecast |
|---|---|---|---|---|
| 범위 | 서울 1개 지점 | 서울 5개 역 | 전국 17개 시도 | 가정 1채 |
| 기간 | 30년(일 단위) | 1년(시간 단위) | 1년(월 단위) | **4년(분 단위 → 집계)** |
| 핵심 | 예측 | 예측 | EDA | **예측** |
| 원본 커밋 | O(15MB) | O(24MB) | O(<1MB) | **X(133MB, gitignore)** |

4개를 합치면 "다양한 시간 해상도·범위·문제 유형(EDA/예측)에서 같은 분석 절차를 반복할
수 있다"는 포트폴리오의 폭이 완성된다.

## 계획 단계에서 이미 정한 것 / 앞으로 진행하며 정할 것

| 지점 | 계획 단계에서 정한 것 | 진행하며 확인해야 할 것 |
|---|---|---|
| 폴더/스크립트 규칙 | 앞 세 프로젝트와 동일하게 `scripts/NN_동작이름.py`, `outputs/{quality,eda,model}` 3분류, `worklogs/YYYY-MM-DD.md` | — |
| 데이터 취급 | `data/raw/`를 이 프로젝트만 gitignore(133MB 제한 초과) | 원본 다운로드 경로를 README에 안내(재현자가 직접 받아야 함) |
| 시간 해상도 | 02단계에서 일단 시간 단위로 집계(EDA용). **모델 타깃 단위는 07~08단계에서 일 단위로 확정**(아래 "타깃 단위" 행 참고) | — (확정됨) |
| 결측 처리 | 82일치 통째 결측 — 완전결측 9일은 제외, 부분결측은 시간별 평균(가용 데이터만)+3시간 이내 보간, 그 이상 공백은 드롭 (02단계에서 확정) | — (확정됨) |
| **타깃 단위** | (신규) 처음엔 "다음 시간" 예측으로 07단계를 진행했으나(폐기), 2026-08-22 사용자와 논의 후 **"다음 날 총 사용량"**으로 확정. 이유: 다음 시간은 관성(같은 활동이 몇 시간 지속)이 너무 강해 persistence를 못 이길 위험이 크고, 실용성도 낮음. "연도별 같은 달"(예: 8월→다음 8월) 방식은 이 데이터가 4년치라 표본이 너무 적어(월 1개당 최대 4번) 기각. 대신 **월/계절을 입력 변수로 포함**시켜, 타깃을 바꾸지 않고도 4년치의 진짜 강점(반복된 계절 패턴)을 모델이 학습하게 한다. | — |
| 모델 비교 구조 | `baseline(평균+persistence) → 랜덤포레스트 → XGBoost` 3종, 튜닝은 이전 프로젝트들처럼 필요성 낮으면 생략 | — |

## 예상 스크립트 순서 (2026-08-22 타깃 단위 변경 반영, 매 단계 승인 받고 진행)

- `01_load_data.py` — 원본 로딩(세미콜론 구분, 결측 `?` 처리), 컬럼 구조·기간·결측 확인
- `02_aggregate_hourly.py` — 분 단위 → 시간 단위 집계 (EDA용, 결측 처리 확정)
- `03_data_quality_check.py` — 결측치·중복값·기초 통계 → `outputs/quality/`
- `04~06_eda_*.py` — 시간대별 패턴, 요일·계절 패턴, 가전 카테고리별 비중 → `outputs/eda/`
- ~~`07_build_next_hour_target.py`~~ — **폐기.** "다음 시간" 타깃으로 만들었다가, 관성 문제로
  방향을 "다음 날"로 바꾸면서 삭제(REPORT.md 부록 Q&A 참고)
- `07_aggregate_daily.py` — 시간 단위 → 일 단위로 재집계(합/평균은 컬럼 성격에 따라 다르게),
  24시간 안 채워진 날은 제외
- `08_build_next_day_target.py` — 다음 날 총 사용량(`next_day_energy_kWh`) 타깃 생성, 누수 검증
- `09_train_test_split.py` — 기준선(평균값+persistence) 계산 + 분할
- `10~12_*_regression.py` — 선형회귀/랜덤포레스트/XGBoost 회귀 비교 (입력에 월/계절 포함 필수)
- `13_model_comparison_chart.py`

## 재현 가능성을 지키려고 정한 것

- 원본 데이터(`data/raw/`, `data/preprocessed/`)는 어떤 스크립트도 고치지 않고 읽기만 한다.
- 표 형식 결과는 CSV로 저장해 값 비교·diff가 쉽게 한다.
- 원본이 gitignore 대상이므로, README에 "다시 돌려보려면" 절에 UCI 다운로드 링크와
  배치 경로를 명확히 안내한다 — 그래야 다른 사람이 이 저장소를 클론해도 재현할 수 있다.
